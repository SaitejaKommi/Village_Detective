### 0.1 Updated product overview

**Product:** a single-player, cinematic, film-noir detective mystery for the browser. The player is a detective who investigates a murder in a rain-soaked mansion by interrogating six AI-powered characters, collecting evidence, and making a final accusation.

**It should feel like:** a Hollywood detective thriller, not a chatbot inside a 2D game.

**Who it is for:** players who enjoy detective and social-deduction games, plus developers and recruiters reading the repo as a multi-agent design example.

**Core differentiator (unchanged):** NPCs have private knowledge and persistent memory, talk to each other, and can lie or withhold information. The backend owns the truth, and LLM output is structured and validated before it affects game logic.

### 0.2 Additional key features

MVP unless marked post-MVP. Priorities are on the Scope page.

1. Short cinematic intro with music, rain, and a title reveal (skippable)
2. Main menu: Start Investigation, Detective Profile, Settings
3. Difficulty selection: Rookie, Professional, Master, changing real game mechanics through server config
4. One authored murder case in a mansion
5. Six NPCs with distinct Hollywood-thriller looks, voices, secrets, and relationships
6. Cinematic interrogation screen: portrait, dialogue history, free-text input
7. Evidence collection and a detective notebook
8. Diamond counter and an optional hint system (server-owned balance)

### 0.3 Additional user stories

- As a player, I want a cinematic opening so the game feels like a film from the first seconds.
- As a player, I want to pick a difficulty so the investigation matches my skill.
- As a player, I want each suspect to look and sound distinct so I can read their personality.
- As a player, I want an interrogation screen with a portrait and transcript so it feels like a scene, not a chat box.
- As a player, I want a notebook so I can compare statements and clues and catch contradictions.
- As a player, I want to spend a diamond on a hint when I am stuck, without being blocked from normal play.
- As a player, I want to earn diamonds for solving cases so I can unlock things later.
- As a developer, I want the diamond balance enforced by the server so the client cannot cheat.

### 0.4 Additional functional requirements

**Presentation and flow**

- FR-26: The client shows a "Click to begin" gate before any audio plays (browser autoplay rules), then the cinematic intro.
- FR-27: The intro is 15 to 20 seconds for the MVP, can be skipped with any key, and ends in the main menu.
- FR-28: The main menu has Start Investigation, Detective Profile, and Settings.
- FR-29: Start Investigation opens difficulty selection (Easy: Rookie Detective, Medium: Professional Detective, Hard: Master Detective), then a short case briefing.
- FR-30: Settings include music volume, effects volume, mute, and skip intro. The choices persist in the browser.

**Case, NPCs, and difficulty**

- FR-31: The MVP ships one authored case, loaded from a case file that defines the victim, the killer, the true timeline, clues, and each NPC's seed memories.
- FR-32: There are six designed NPCs (see Character Bible). Each has a portrait, voice style, secret, motive to lie, and relationships.
- FR-33: The client sends the chosen difficulty in `start_case`. The server loads a difficulty config that changes NPC prompt directives, active red herrings, clue visibility, hint cap, and reward.
- FR-34: The solution (killer, full timeline) is never sent to the client before the accusation is resolved.

**Interrogation and investigation**

- FR-35: The interrogation screen shows the NPC portrait, name and role, the full dialogue history, free-text input (300 character limit), and a thinking indicator while a reply is pending.
- FR-36: Evidence collection and NPC conversations are always free.
- FR-37: The notebook lists collected clues and notable NPC statements.

**Diamonds, hints, profile**

- FR-38: Each player has a persistent profile: `playerId`, diamonds, cases solved, current outfit (default only in MVP).
- FR-39: New players start with 3 diamonds.
- FR-40: `hint_request` is handled by the server: check balance, deduct 1 atomically, return a hint. The client never sends or sets a balance.
- FR-41: Hints are templated from the truth log and case data, tiered (direction, location, contradiction pointer), never name the killer, and are capped per case by difficulty.
- FR-42: A correct accusation grants a diamond reward by difficulty, once per case run, server-side. Proposed: Easy +1, Medium +2, Hard +3.
- FR-43: A player with 0 diamonds can still complete the case.

**Audio and ending**

- FR-44: Audio includes menu music, investigation music, a rain loop, footsteps, and UI sounds.
- FR-45: The case ending shows win or lose, the true timeline, each NPC's secret, and diamonds earned.

### 0.5 Additional non-functional requirements

- **Visual consistency:** colors, fonts, and spacing are defined once as design tokens (CSS variables) and reused everywhere.
- **Load time:** the intro and menu should be interactive within a few seconds on a normal connection. Lazy-load audio and portraits. Keep the initial asset payload small (target under about 25 MB, to be checked).
- **Audio:** audio only starts after a click. Mute state persists. Every sound asset has a checked free license.
- **Accessibility basics:** text meets WCAG AA contrast on dark backgrounds, menus work with the keyboard, `prefers-reduced-motion` disables lightning flashes and strong motion, and no effect flashes more than three times per second.
- **Perceived latency:** hide LLM delay with a thinking animation on the portrait. Interrogation uses the fast model and short prompts.
- **Integrity:** diamond changes are atomic server-side updates. Client balance display is read-only.
- **Spoiler safety:** only the killer's agent gets the cover-story instruction. Other agents never receive the solution.

### 0.6 Updated user flow

1. Open the game, see "Click to begin", click.
2. Cinematic intro plays (skippable) and fades into the main menu.
3. Player picks Start Investigation, Detective Profile, or Settings.
4. Start Investigation leads to difficulty selection.
5. Client sends `start_case` with the difficulty. Server loads the case and replies with the briefing.
6. Case briefing: victim, scene, who was in the house.
7. Investigation: walk the mansion, approach NPCs, interrogate, inspect clues, review the notebook.
8. Optional: request a hint (costs 1 diamond, server confirms).
9. Accusation: choose a suspect and confirm.
10. Case ending: reveal, true timeline, diamonds earned, back to the menu.

## Original PRD (sections 1 to 9)

Everything below is the original PRD, kept for the technical requirements and history.

## 1. Overview

**Product:** Village of Liars, a single-player 2D murder-mystery browser game.

**What it does:** A murder happens in a small village. Six to eight villagers, each an LLM agent with a secret and a memory, move around, talk to each other, and lie. The player investigates by walking around and chatting with them, then accuses one villager.

**Who it is for:**

- Players who like detective and social-deduction games
- Developers and recruiters looking at the repo as an example of multi-agent design

**Core design principle:** The server owns the truth. Agents receive perceptions and return structured actions. The server validates and applies them.

## 2. Key features

1. Top-down 2D village with 6 rooms and 6 to 8 NPCs. ⚠ Superseded for the MVP: mansion setting and exactly six designed NPCs. See section 0 above and the Conflicts and Open Questions page, items 1 and 4.
2. Free-text chat with any NPC
3. NPCs with persona, secret, goal, and persistent memory
4. NPC-to-NPC gossip when they are in the same room
5. Engine-controlled murder with a deterministic killer, time, and victim
6. Clue system: physical clues in rooms plus testimony from NPCs
7. Accusation flow with win/lose result and reveal screen
8. Debug overlay showing each NPC's recent perceptions, memory, and last action (also used for the video)
9. Optional NPC voices via browser `speechSynthesis`

## 3. User stories

**Player**

- As a player, I want to walk around the village so I can find people and places.
- As a player, I want to chat freely with a villager so I can question them my own way.
- As a player, I want villagers to remember what I asked earlier so conversations feel real.
- As a player, I want villagers to have different personalities so I can tell them apart.
- As a player, I want to find physical clues so I have evidence beyond what people say.
- As a player, I want to accuse a villager and see whether I was right.
- As a player, I want a clear indication of the time and the current objective.

**Developer / viewer**

- As a developer, I want to see agent reasoning and memory in a debug overlay so I can understand why an NPC lied.
- As a developer, I want LLM failures to degrade gracefully so the game never stalls.

## 4. Functional requirements

### Game world

- FR-1: The server maintains a world state: rooms, entity positions, game clock, and an append-only truth log.
- FR-2: The server runs a tick loop (e.g. 1 tick per second) and advances the game clock.
- FR-3: NPCs move between rooms following simple schedules; the LLM chooses among valid options only.
- FR-4: The server broadcasts world state updates to the client over WebSocket.

### Agents

- FR-5: Each NPC has a persona, a secret, a goal, and a memory list `{t, text, importance}`.
- FR-6: Agents are triggered by new perceptions (event-driven), not on every tick.
- FR-7: Agent output must match a Zod schema: `{action, say?, target?, thought?}`. On parse failure, retry once, then fall back to a safe default action (`idle`).
- FR-8: The server validates each action against world rules (e.g. cannot move to a non-adjacent room) before applying it.
- FR-9: When two NPCs share a room, they can exchange information, and the exchange is added to both memories.
- FR-10: Memory retrieval for prompts uses recency plus keyword overlap, returning the top-k entries.

### Murder and investigation

- FR-11: At a scheduled game time, the engine picks the victim and killer deterministically (seeded) and creates the murder event in the truth log.
- FR-12: The killer agent receives a "cover story" instruction; it does not decide who dies.
- FR-13: The server generates clues from the truth log (e.g. "muddy boots in Kitchen") and places them in rooms.
- FR-14: Witnesses perceive only what was in their room at the time.

### Player interaction

- FR-15: The player can move with arrow keys or WASD.
- FR-16: The player can open a chat with an NPC in range and send free-text messages.
- FR-17: NPC replies come from the LLM using persona, secret, memory, and the player's message.
- FR-18: The player can inspect clues in the current room.
- FR-19: The player can accuse an NPC once. The server compares with the truth and returns win or lose plus a reveal summary.

### LLM infrastructure

- FR-20: A single `LLMProvider` interface wraps Groq and Gemini.
- FR-21: Calls go through a queue with rate limiting, staggering, and identical-prompt caching.
- FR-22: If the primary provider fails or is rate-limited, fall back to the second provider.

### Persistence

- FR-23: Each game session gets a guest session ID (UUID).
- FR-24: The server stores sessions, chat transcripts, and results in SQLite.
- FR-25: A JSON snapshot of the world can be saved and loaded (for debugging and demos).

## 5. Non-functional requirements

**Performance**

- Client renders at 60 FPS on a normal laptop.
- Player chat reply latency target: under 3 seconds typical (use the fast model, short prompts).
- Ambient NPC calls must not block the tick loop.

**Reliability**

- The game never crashes or soft-locks from malformed LLM output.
- LLM outage or rate limit leads to fallback provider, then to scripted fallback lines.

**Security**

- API keys live only on the server, in `.env`, never in the client bundle.
- Player text is length-limited (e.g. 300 chars) and treated as untrusted input in prompts.
- Prompt-injection hardening: the system prompt tells agents to stay in character and never reveal their instructions. The server never executes anything from LLM text, only validated actions.
- Basic per-session rate limit on chat messages.

**Usability**

- Controls are explained in the first 10 seconds.
- A visible objective and clock are always on screen.
- Chat UI shows who is talking and a typing indicator.

**Maintainability**

- A single shared `types.ts` contract used by both client and server.
- TypeScript strict mode on both sides.
- README plus these docs explain how to run and extend.

**Cost**

- Free tiers only. Call volume stays within provider limits through event-driven triggers and caching.

## 6. User flow (original, superseded by section 0.6 above)

1. Player opens the game and sees a title screen with a **Start** button and a short controls note.
2. Client opens a WebSocket, receives a session ID, and loads the village.
3. A short intro text sets the scene: "Someone in this village will not live to see tomorrow."
4. Player explores, and NPCs move and talk among themselves.
5. The murder event fires. A bell rings and the victim is found.
6. Player investigates: walks to rooms, inspects clues, and chats with NPCs.
7. Player may open the notebook/debug view for a list of collected clues and statements.
8. Player clicks **Accuse**, picks an NPC, and confirms.
9. Server compares with the truth. The reveal screen shows win or lose, the real timeline, and each NPC's secret.
10. Player can restart with a new seed.

## 8. Out of scope for v1

Multiplayer, accounts, mobile, deployment, embeddings, LLM-chosen killer, multiple cases, detective wardrobe and customization, spending diamonds on anything except hints. See the README "Future work".

## 9. Success criteria

- A full playthrough works start to finish without errors.
- At least one moment where an NPC's lie is contradicted by another NPC's memory (this is the video highlight).
- Repo has a clear README and architecture explanation.
